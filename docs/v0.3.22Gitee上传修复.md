# v0.3.22 Gitee 上传修复

用户在网站管理中上传本地 GitHub 增量词条时，v0.3.21 提示“无法确定文件版本，未上传”。错误发生于写入前的 Gitee 文件版本查询，未清除本地词库和待上传修改。

2026-10-31 使用 Gitee 公开仓库 `sdk/gitee5j` 进行只读验证：正常文件的 Contents API 返回文件对象；不存在的普通路径和 `dictionaries/github.com/zh-Hans/managed-entries.json` 均返回 HTTP 200 与空数组 `[]`，提交历史也为空。旧实现只判断 HTTP 成功，误将空数组当作已有文件，随后无法获得最近提交。已用回归测试复现同一错误。

修复后的 `dictionary-publish.js` 按 HTTP 200 空数组或 HTTP 404 判为新文件，使用 create 操作；已有文件须返回正确的 type、path 和 blob SHA，继续查询最近提交作为 last_commit_id。非空目录、格式错误和历史查询失败仍停止，不绕过版本保护。三个协议文件仍在一次提交中发布，并保留事务确认、并发检查和 v0.3.21 的冲突确认规则。

API 的文件内容对象及 last_commit_id 含义根据 [Gitee 官方 API 文档](https://gitee.com/api/v5/swagger) 与其 `/api/v5/doc_json` 定义核对。空数组行为为公开接口实际观察结果，不能假定所有缺失路径均只返回 404。

回归覆盖新建文件、已有文件、无效元数据、无法确定历史、并发拒绝与响应丢失。隔离 Edge 后台模拟与实际观察一致的 HTTP 200 空数组，并验证首次创建增量文件与两个清单更新在一次提交中完成。

只构建 Edge 解压目录，不打包、不安装、不操作个人浏览器、不向真实仓库写入。公开 GET 验证不等于用户私有仓库实际上传验收。

本轮验证：构建通过，`npm test` 194 项通过，隔离 Edge 后台集成 56 项通过，构建一致性及 `git diff --check` 通过。新增文件回归先复现原错误再验证修复；记录见忽略的 `.cache/v0.3.22-verification.json`。
